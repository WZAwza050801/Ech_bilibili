3深挖 A · 切分帧的三种流派

"怎么决定在哪些时间点截画面"是画面通道的第一道分水岭。调研发现三种流派，智能度和成本差异极大。

🥇 流派 A：场景检测 + 均匀骨架融合（let-ai-read-video）

scripts/frames.py 全场最精巧的选点算法。三模式 scene / uniform / auto，默认 auto 的融合逻辑：

# auto 模式选点（frames.py :: plan_points）
backbone_n = max(1, (n + 1) // 2)          # ① 至少 50% 预算做均匀"时间骨架"——保证片尾不裸奔
kept = [(t, "uniform") for t in uniform_points(start, end, backbone_n)]
scene_selected = select_max_spacing(scene_pts, [t for t,_ in kept], slots)
                              # ② 剩余预算给场景切换点，但用 max-min 间距选择：每轮挑
                              #    离已选点最远的候选，防止补点全部挤在片头
grid = [start + i*(end-start)/grid_n ...]  # ③ 场景点不足时，从 8n 密度的细网格继续 max-min 补齐

四层防线保证工程可靠性：

1

硬预算闸门：全局 2fps / 100 帧硬上限；按片长分档预算（≤30s→30 帧，≤60s→40，≤180s→60，≤600s→80，更长→100）。定向补帧模式才允许提到 4fps / 0.25s 最小间隔。

2

精确时间戳：抽帧用 -ss 前置（先关键帧定位再精确解码），并通过 showinfo 读回实际解码 PTS 作为 actual_t——区别于请求的 requested_t。这解决了"请求 t=12.3 但关键帧量化后实际落在 12.27"的对齐漂移问题。

3

失败重试：单点抽帧失败自动回退 t-0.6s 重试一次（躲开转场黑帧/EOF）；4 线程并行抽帧，pending 临时文件 + os.replace 原子落盘，失败帧不污染索引。

4

索引即契约：frames.json 每帧记录 file / t / requested_t / actual_t / source / pass_id / width，多轮补帧用 pass_id 溯源，追加模式按 actual_t 以 0.001s 碰撞阈值去重（保留 4fps 补帧的密集证据，只删真正落在同一解码帧的）。

🥈 流派 B：按片长分档均匀抽帧 + 帧缓存（claude-video-vision）

extractors/frames.ts 策略简单但胜在会省钱——按分辨率缓存帧，同一帧绝不抽两次：

// 按时长分档 fps（frames.ts :: calculateAutoFps）
if (durationSeconds < 60) return 2;
if (durationSeconds < 300) return 1;
if (durationSeconds < 900) return 0.5;
if (durationSeconds < 3600) return 0.2;
return 0.1;                              // 1小时以上 → 0.1fps，每10秒1帧

// manifest.ts :: getUncachedTimestamps —— 换分辨率/换问题时只补缺失帧
export function getUncachedTimestamps(manifest, resolution, wanted) {
  const cached = new Set(manifest.resolutions[resolution]?.frames.map(f => f.timestamp));
  return wanted.filter(ts => !cached.has(ts));
}

真正的巧思在自适应交互：它把选点权交给主模型——Claude 可以先粗看一遍，再针对感兴趣的时间窗调用 video-detail 提高 fps、缩窗、换分辨率重抽。另有 agents/frame-describer.md 子代理把每帧转成文字描述（"Frame at [timestamp] — 描述人物/屏幕文字/物体/变化"），用文字代替图片进上下文，token 消耗降一个数量级，代价是丢失细节。

🥉 流派 C：固定间隔暴力抽帧（openclaw-video-vision）

src/index.js：默认每 5 秒 1 帧、硬上限 20 帧（fps=1/${interval}），超长视频自动拉大间隔 max(interval, ceil(duration/maxFrames))。实现最简单（20 分钟视频只有 20 帧），适合"这个视频大概讲什么"级别的省流，无法支撑完整内容整理。它的亮点反而在抓取层：Playwright 爬虫 + yt-dlp 双路兜底 + cookie 管理。

4深挖 B · 语音提取与时间对齐

语音通道的关键不是"能不能转写"，而是转写结果的时间轴和帧的时间轴能不能对上。各项目的做法差异很大。

项目字幕/ASR 策略音频切分对齐机制
let-ai-read-video字幕直取优先（VTT/SRT 解析器：去自动字幕滚动重复、相同文本连续块合并）→ 无字幕时 ffmpeg 抽 16kHz 单声道 wav → faster-whisper（vad_filter=True, condition_on_previous_text=False 防幻觉滚雪球）或 SenseVoice不切，整段送 whisper⭐ 双向精确：转写 segment 带起止秒，帧带 actual_t，review.json 把两者装进同一时间窗；补帧计划用绝对秒数
claude-video-vision多后端：Gemini API（直接听音频）/ 本地 whisper / OpenAI API⭐ silencedetect 智能切分（见下）统一 formatHMS 时码工具，chunk 带 overlap 衔接
video-to-notesyt-dlp 元数据里挑 track：语言优先级 zh-Hans→zh-Hant→zh→en→ja→ko，扩展名优先 vtt→srt→ttml→json3；manual 字幕优先于 auto不切summary 中的每个要点 bullet 必须携带 [mm:ss-mm:ss] 且需与 transcript 核对
bilibili-summary-agent⭐ 纯 API 直连：api.bilibili.com/x/web-interface/view 拿 cid → 字幕接口拿 list；还从视频页 HTML 的 window.__INITIAL_STATE__ 提取权威字幕 ID 列表做交叉校验（比 API 更可靠）—字幕原生带时间戳
openclaw-video-vision本地 whisper 或关闭转写整段帧与转写仅"同时呈现"给模型，无结构化对齐

最值得抄的音频切分：静音检测切 chunk（claude-video-vision）

extractors/audio-chunker.ts——长视频不能整段塞给 whisper（显存/上下文限制），乱切又会把句子腰斩。它的方案是让 ffmpeg 的静音检测决定下刀位置：

// 两档阈值找静音区间
default: "silencedetect=n=-40dB:d=0.5"   // 安静环境：-40dB、持续0.5s以上
loose:   "silencedetect=n=-30dB:d=0.2"   // 吵闹环境兜底：-30dB、0.2s

// 切分逻辑：理想边界 = chunkSize 的整数倍；每个边界在 ±30s 容差内
// 找最近的静音中点，把刀口移过去（clean_cut=true）；找不到的标记
// clean_cut=false 并在 chunk 元数据中告知下游"此处可能有截断"
TOLERANCE_SECONDS = 30;  chunk 之间再补 overlap 重叠，防止跨 chunk 丢词

这个设计对我们的 agent 直接可用：切分由音频内容而非固定秒数决定，切点天然落在停顿处。

B站字幕获取的三条路（按优先级）

1

yt-dlp 带 SESSDATA cookie 直取 AI 字幕（video-to-article-skill 验证可行）：生成 Netscape 格式 cookies.txt，--write-auto-subs --sub-lang zh-Hans --cookies cookies.txt。零计算成本，注意 SESSDATA 有时效。

2

B站 Web API 直连（bilibili-summary-agent）：view 接口→cid→字幕列表，用页面 __INITIAL_STATE__ 交叉校验字幕 ID。最适合批量/程序化场景，需要处理风控。

3

Whisper 本地兜底（let-ai-read-video 实测：NVIDIA GPU 下 1 小时视频转写 3~5 分钟，27~53 倍速）。关键参数：condition_on_previous_text=False 防止幻觉复读，VAD 过滤静音段。

5深挖 C · 素材处理与 Agent 编排

拿到转写+帧之后，怎么组织成"可审查、可补强、可落盘"的素材包？这是各家工程功力的试金石。

let-ai-read-video：证据驱动的补帧闭环（全场唯一）

🎬
watch.py 首轮
转写 + 抽帧 → transcript.json / frames.json / review.json
🔍
模型审查
逐时间窗判断文-画关系，填 assessment
📋
review.py plan
insufficient 窗口 → refine_plan.json（区间或精确点）
🎯
refine.py --append
定向补帧，4fps 上限，保留首轮帧
♻️
review.py refresh
只重置受新增帧影响的窗口，复查

审查的核心是一套文-画关系标签体系，避免模型乱补帧：

// 每个时间窗的判断输出（adaptive-review.md 协议，平台无关）
{ "assessment": {
    "relation": "insufficient",   // supports(画面支持文稿) / complements(互补)
                                  // / contradicts(矛盾) / unrelated(B-roll) / insufficient(证据不足)
    "confidence": 0.86,
    "notes": "讲话要求查看右侧曲线，但最近帧距该时刻 4.2 秒",
    "refine": true              // 只有 insufficient 允许触发补帧
}}
// 停止条件：窗口转为 supports/complements，或补满2轮，或累计120帧封顶，
// 或时间间隔已缩到0.25s——多层止损防止无限循环烧钱

这是全场唯一把"模型判断 → 代码校验 → 增量取证"做成结构化闭环的设计：模型只输出中立 JSON 计划，代码负责校验合法性（时间在窗口内、fps 不超标、去重），再执行。模型与代码职责分离得很干净。

claude-video-vision：MCP 会话缓存

session/manifest.ts 以视频 hash 为 key 建 session manifest，按 分辨率/格式 二级索引缓存帧。同一视频反复提问时（先问概述、再问某段细节），已抽的帧直接复用，只有新时间窗才调 ffmpeg。配合"模型自适应调参"（Claude 自己决定 fps/时间窗），实现渐进式观看：粗看→细看特定段落。

局限：没有把转写和帧装进同一时间窗的结构——模型要自己对时间戳。

video-to-notes：目录即数据库

每个视频一个 folder，输出契约固定五件套：metadata.json / transcript.txt / summary.md / tags.json / report.html。transcript_source 枚举只有三个合法值：manual_subtitle / auto_subtitle / local_whisper——来源可追溯是硬约束。还有本地 dashboard（serve_dashboard.py）聚合所有已处理视频，支持全文搜索。

这套"输出契约 + 来源枚举 + 索引页"的工程化模式值得整体照搬。

6深挖 D · 写作输出 Agent

离你的需求最近、也最令人意外的一层：所有项目的"写作 agent"都不是代码，而是 prompt 规范 + 模板。质量差距完全取决于规范写得有多细。

video-to-article-skill：输出层的宝库（但地基不稳）

它的写作编排全是 prompt 指令，没有一行代码做分段处理。但输出矩阵设计得最完整：

输出平台文体选项载体
公众号热点解读 / 深度长文 / 金句提炼 / 故事叙述.md + .html 预览
小红书种草安利 / 干货教程 / 情感共鸣 / 清单盘点.txt + .html 预览
口播稿爆款开场 / 故事叙述 / 清单列表 / 对话挑战 / 情绪共鸣.txt + .html 预览
HTML 文章5 套完整设计系统（蓝白商务/Notion深色/Claude风/暗黑科技/极简现代，含完整 CSS 变量表）.html

写作质量控制有真东西——内容完整性检查清单：

✓

80% 覆盖率红线：明确要求"使用 80% 以上的字幕内容，不过度删减；文章长度与视频时长成比例"——这正是"完整整理"区别于"摘要"的核心指标；

✓

缺失检测三件套：主题一致性比对（识别原文 topics 与文章 topics 的差集）、关键词覆盖率计算、关键信息逐条核对；

✓

来源标注规范：按平台预置了来源说明模板（公众号在标题下、小红书在开头或结尾、口播稿双处必标），规避搬运判定。

致命短板：它让 Claude 一次性读完整个字幕直接成文。20 分钟视频字幕约 6k 字尚可，1 小时以上必然爆上下文或被隐性截断——"80% 覆盖率"在长视频上是无法兑现的口号。

let-ai-read-video：唯一认真处理"长视频怎么写"的项目

references/summary-template.md 的撰写规范，逐条都是可以直接搬进自研 agent prompt 的：

# 规范第 5 条：超长视频的 map-reduce（原文）
"用 map-reduce——按 10～15 分钟一段分批读 transcript 做分段笔记，
 再汇总成各章节；不要一次性通读后凭印象写。"

# 规范第 2 条：证据边界（反幻觉的硬约束）
"内容必须基于 transcript 原文与抽帧画面，两者都没有的信息不得编造、
 不得脑补；证据不足就明说「转写与抽帧均未覆盖」。"

# 规范第 3 条：引文修正（对 AI 字幕/whisper 错字的务实处理）
"讲师口语、口误与 AI 字幕/whisper 的同音错字按语境修正后再引用，
 不照抄明显错误；修正幅度较大时用「（大意）」标注。"

# 规范第 6 条：章节表必须"覆盖全片、时间首尾相接"——结构完整性可机械校验

输出模板结构：视频信息表 → 一句话总结 → 内容脉络表（全片时间轴）→ 逐章详解（核心论点/带时间戳要点/关键例子/小结）→ 关键概念表（术语/解释/首次出现时间）。交付"三大件"：阅读总结 .md + 文字稿 .docx + 关键帧 .pdf。

video-to-notes：answer-first 写作契约

references/reporting.md 定义了另一种写作风格：结论先行 + 全 bullet 强制时间戳。

Summary
  一段话说明视频核心结论。
Key Points
  - [mm:ss-mm:ss] 主要结论/主张/方法/风险/决策
    - [mm:ss-mm:ss] 支撑例子、数字、注意事项（可选嵌套）
Notes
  - 只写影响可信度的字幕/转写/来源/完整性警告

三条有意思的规则：① "Do not invent precision"——时间戳精度不得超出 transcript 支持的范围；② 长视频（转写 >45 分钟）先按连续时间段分片做笔记、合并时去重、最后对照全片 transcript 核验所有时间戳——这是朴素的 map-reduce，但缺少 let-ai 那种逐段结构；③ tags.json 的标签白名单清洗规则（禁止 workflow 类标签混入）。

写作层调研小结：三家共同点——时间戳贯穿全文（可回溯到视频位置）；差异点——let-ai 解决了"长视频怎么分段写"（map-reduce + 章节表机械可验），video-to-article-skill 解决了"写成什么平台文体"（但长视频撑不住），video-to-notes 解决了"怎么保证可信"（来源枚举+禁止编造精度）。你要的"公众号推文级完整整理"，恰好需要这三者的交集，而交集目前是空集。

8对自研项目的启示：直接可抄的零件清单

🔧 抄这些代码级设计

A

选点算法 ← let-ai frames.py：均匀骨架 + max-min 场景点融合 + 预算分档。整段函数可直接移植（纯 Python + ffmpeg，无黑盒依赖）。

B

actual_t 精确回读 ← showinfo PTS：所有"引用时间戳"用实际解码时刻，引用可信度直接决定文章可回溯性。

C

静音点切音频 ← claude-vv audio-chunker：silencedetect 两档阈值 + ±30s 边界吸附 + chunk overlap，喂 whisper 或分段多模态都好用。

D

B站字幕双路 ← yt-dlp+SESSDATA 直取 AI 字幕为主，API 直连为备，whisper 兜底；whisper 参数 condition_on_previous_text=False 防幻觉。

E

模型-代码分离契约 ← let-ai 的 RESULT_JSON 单行协议 + 中立 JSON 补帧计划：模型只出计划，代码校验执行，天然防越权。

✍️ 抄这些写作规范

A

map-reduce 成文法 ← let-ai：>45min 视频强制按 10-15 分钟分段做结构化分段笔记（带时间戳），再按章节合并——这是"完整整理"在工程上成立的前提。

B

证据边界 + 引文修正 ← let-ai：不编造、标注（大意）、错字按语境修。写公众号文章时同样要区分"视频说的"和"整理者的补充"。

C

完整性红线 ← video-to-article：80% 覆盖率 + 主题差集检测 + 关键信息核对清单；配合 reduce 阶段真正可执行。

D

平台×文体输出矩阵 ← video-to-article：公众号四文体 prompt + 来源标注模板 + 文件命名规范，可直接嫁接你 D 盘已有的公众号工具链。

E

禁止编造精度 ← video-to-notes：时间戳只写 transcript 支持的粒度，标签白名单清洗。
